= Exercise 5: Webhook notifier
:navtitle: Exercise 5: Webhook notifier

Estimated time: 15 minutes.

RHACS can push policy violation alerts to external systems using *notifiers*.
A *Generic Webhook* notifier sends a JSON payload via HTTP POST to any endpoint.
That pattern is how many teams feed a monitoring or ticketing stack after a small transform layer.

In this lab you use https://webhook.site[webhook.site] as the receiver so you can inspect the raw ACS payload.
Mapping into a live monitoring product stays discussion-only.

== Task 5.1: Create an external webhook receiver

. Open https://webhook.site in a new browser tab.
. Copy the unique URL that is generated automatically.
. Leave the tab open so you can watch incoming requests.

NOTE: Outbound HTTPS from this Showroom to webhook.site was verified during lab authoring. If your instance blocks it, ask the instructor for an in-cluster receiver URL instead.

== Task 5.2: Create a Generic Webhook notifier in ACS

. In the RHACS Console, navigate to *Platform Configuration* > *Integrations*.
. Under *Notifier Integrations*, click *Generic Webhook*.
. Click *Create integration*.
. Fill in:
+
[cols="1,2",options="header"]
|===
|Field |Value

|Integration name
|`Lab - Webhook`

|Endpoint
|_(paste your webhook.site URL)_

|Skip TLS verify
|Enabled

|Audit logging
|Disabled
|===
+
. Click *Test* and confirm a request appears in webhook.site.
. Click *Save*.

== Task 5.3: Attach the webhook to a policy

. Navigate to *Platform Configuration* > *Policy Management*.
. Open the enabled policy *Latest tag*.
. Click *Actions* > *Edit policy*.
. Open *Policy behavior*.
. Under *Notification*, select `Lab - Webhook`.
. Save.

== Task 5.4: Trigger a violation and inspect the payload

. On the bastion, create a pod that uses the `latest` tag in the `backend` namespace:
+
[source,bash]
----
oc run webhook-trigger --image=image-registry.openshift-image-registry.svc:5000/openshift/httpd:latest -n backend
----
. Wait a few seconds.
. In webhook.site, open the new POST request and review the JSON.
. Confirm the payload includes policy name `Latest tag`, deployment `webhook-trigger`, and namespace `backend`.

== Task 5.5: Discussion: mapping to a monitoring system

A production path would often:

. Accept the ACS webhook JSON in a small middleware service.
. Map fields into a monitoring or ticketing event, for example:
** Host: deployment namespace
** Service: policy name
** State: derived from ACS severity
** Output: violation summary
. Forward that result to the organization's monitoring platform.

This lab stops at the ACS JSON payload. The payload already contains the fields needed for that mapping.

== Cleanup

[source,bash]
----
oc delete pod webhook-trigger -n backend --ignore-not-found
----

. Edit *Latest tag* again and remove `Lab - Webhook` from notifications before you leave the exercise.

== Key takeaways

* Generic Webhooks are the flexible bridge into existing monitoring stacks.
* The ACS JSON payload includes policy, deployment, and violation context.
* webhook.site is for labs. Production uses middleware in front of the real monitoring or ticketing tools.
