= Exercise 3: Scoped Access Control and OIDC mapping
:navtitle: Exercise 3: SAC and OIDC

include::partial$session2-ui.adoc[]

Estimated time: 25 minutes.

RHACS *Scoped Access Control* (SAC) controls what each user can see and do inside a shared ACS Central.
SAC uses three primitives:

* *Permission Set*: what a user can do (read images, manage access, and so on).
* *Access Scope*: where those permissions apply (which clusters and namespaces).
* *Role*: one Permission Set plus one Access Scope.

You will create a tenant-scoped role for the `payments` namespace, map a Keycloak group to that role, and prove isolation with a test user login.

By the end of this exercise you will:

* Build the three SAC primitives (Permission Set, Access Scope, Role) for a single-namespace tenant.
* Configure a Keycloak OIDC realm, client, group, and user from scratch.
* Map a Keycloak group claim to an ACS role so tenant isolation is automatic.
* Prove isolation by logging in as a scoped user and confirming restricted visibility.
* See scoped vulnerability data in the OpenShift Console via the ACS Console Plugin.

== Task 3.1: Review default roles

. In the RHACS Console, navigate to *Platform Configuration* > *Access Control*.
. Open the *Roles* tab and review the built-in roles (*Admin*, *Analyst*, *Vulnerability Management Approver*, *Vulnerability Report Creator*).
. Note any demo roles already present (for example `demo-team-a-dev`). You will create a separate lab role instead of reusing them.

== Task 3.3: Create a Permission Set

. Open the *Permission sets* tab.
. Click *Create permission set*.
. Enter:
** *Name:* `lab-vuln-reader`
** *Description:* `Read-only access to images, vulnerabilities, and deployments.`
. Start from *No access* on every resource, then set only:
+
[cols="1,1",options="header"]
|===
|Resource |Access level

|Alert
|Read access

|CVE
|Read access

|Deployment
|Read access

|Image
|Read access

|WatchedImage
|Read access
|===
+
Leave every other resource at *No access* (including `Access`, `WorkflowAdministration`, and integration-related resources).
. Click *Save*.

NOTE: RHACS {rhacs-version} permission sets do not use a resource named `Policy`. Policy pages are gated by other resources such as workflow or access administration. Keeping those at *No access* is enough for a read-only vuln viewer.

== Task 3.5: Create a Keycloak realm, client, group, and user

Keycloak is pre-installed in this Showroom.
Use the bastion `oc` CLI to discover the console URL and the temporary admin credentials yourself (do not guess a static password).

=== Get the Keycloak URL and admin credentials

. On the bastion, print the Keycloak route and admin console URL:
+
[source,bash]
----
SSO_HOST="$(oc get route keycloak -n keycloak -o jsonpath='{.spec.host}')"
echo "Keycloak base URL:  https://${SSO_HOST}"
echo "Admin console URL:  https://${SSO_HOST}/admin"
----
. Print the temporary admin username and password from the operator bootstrap secret:
+
[source,bash]
----
echo -n "Username: "
oc -n keycloak get secret keycloak-initial-admin -o jsonpath='{.data.username}' | base64 -d
echo
echo -n "Password: "
oc -n keycloak get secret keycloak-initial-admin -o jsonpath='{.data.password}' | base64 -d
echo
----
+
The username is typically `temp-admin`. The password is generated per environment.

TIP: You can also copy the SSO URL from the Showroom dashboard. The CLI values above are the source of truth when the dashboard and cluster disagree.

=== Sign in to the admin console

. Open the *Admin console URL* from the previous step (path `/admin`).

=== Create the `acs-central` OpenID Connect client

. In realm `rhacs-lab`, open *Clients* and click *Create client*.
+
image::s2/s2-03-keycloak-clients-list.png[Clients list with Create client action,width=720]
. On *General settings*:
** *Client type:* OpenID Connect
** *Client ID:* `acs-central`
+
image::s2/s2-03-keycloak-create-client-general.png[Create client General settings with Client ID acs-central,width=720]
. Click *Next*.
. On *Capability config*, set *Client authentication* to On (leave *Standard flow* enabled).
+
image::s2/s2-03-keycloak-create-client-capability.png[Create client Capability config with Client authentication On,width=720]
. Click *Next*.
. On *Login settings*, set *Valid redirect URIs* to Central's OIDC callback URL.
+
RHACS Central on OpenShift is exposed through a *reencrypt* Route (TLS terminates at the router, then re-encrypts to Central).
Keycloak must allow the hostname from that route, which is the same URL you use for the RHACS Console in the browser.
Do not use an edge-only alternate host or an in-cluster service DNS name.
+
On the bastion, list the Central-related routes so you can see which one uses *reencrypt* termination:
+
[source,bash]
----
oc get route -A -o custom-columns=\
NAMESPACE:.metadata.namespace,NAME:.metadata.name,HOST:.spec.host,TERMINATION:.spec.tls.termination \
  --no-headers | awk 'tolower($2) ~ /central/ || tolower($3) ~ /central/'
----
+
The route with `reencrypt` termination is the one Keycloak needs for its redirect URI.
Now extract the callback URL from that route:
+
[source,bash]
----
CENTRAL_HOST="$(oc get route -A -o custom-columns=\
NAME:.metadata.name,HOST:.spec.host,TERMINATION:.spec.tls.termination \
  --no-headers | awk 'tolower($1) ~ /central/ && $3 == "reencrypt" { print $2; exit }')"

# Fallback if the filter finds nothing: use the bastion Central address
if [ -z "$CENTRAL_HOST" ]; then
  CENTRAL_HOST="${ROX_CENTRAL_ADDRESS#https://}"
  CENTRAL_HOST="${CENTRAL_HOST%%/*}"
fi

echo "https://${CENTRAL_HOST}/sso/providers/oidc/callback"
----
+
Copy the printed callback URL into *Valid redirect URIs*.
Confirm it matches the host in your RHACS Console browser URL.
+
image::s2/s2-03-keycloak-create-client-login.png[Create client Login settings with Valid redirect URIs field,width=720]
. Click *Save*.
. Open the client *Credentials* tab and copy the *Client secret* (you need it in Task 3.6).
+
image::s2/s2-03-keycloak-client-credentials.png[acs-central Credentials tab with Client secret,width=720]

image::s2/s2-03-keycloak-create-user.png[payments-dev user details with Email and Email verified settings,width=720]

+
image::s2/s2-03-keycloak-user-password.png[Set password dialog with Temporary Off,width=720]

+
image::s2/s2-03-keycloak-user-groups.png[Join group dialog selecting lab-payments-devs,width=720]

IMPORTANT: If *Email verified* is Off or a required action remains, Keycloak returns `Account is not fully set up` and the ACS login fails.

== Task 3.6: Add the OIDC auth provider in ACS

. Return to RHACS > *Platform Configuration* > *Access Control* > *Auth providers*.
. Click *Create auth provider* > *OpenID Connect*.
. Fill in:
+
[cols="1,2",options="header"]
|===
|Field |Value

|Name
|`Keycloak - rhacs-lab`

|Issuer
a|On the bastion, print the issuer URL:
[source,bash]
----
echo "https://$(oc get route keycloak -n keycloak -o jsonpath='{.spec.host}')/realms/rhacs-lab"
----
Copy the printed value into the *Issuer* field.

|Client ID
|`acs-central`

|Client Secret
|_(from Task 3.5)_

|Mode
|Auto-select
|===
+
. Under *Rules*, add:
** *Key:* `groups`
** *Value:* `lab-payments-devs`
** *Role:* `lab-payments-vuln-reader`
. Change the *Minimum access role* (the default row with an empty key and value) from *Admin* to *None*.
+
IMPORTANT: ACS pre-fills the default rule with *Admin*. If you leave it, every user who logs in through this provider gets full Admin access regardless of their group membership, and the group-to-role mapping is effectively ignored. Setting it to *None* ensures only users matching the `groups` rule receive the `lab-payments-vuln-reader` role.
. Click *Save*.

== Task 3.7: Prove tenant isolation

. Open a private or incognito browser window.
. Open the RHACS Console URL.
. Choose *Keycloak - rhacs-lab* and log in as `payments-dev`.
. Verify:
** *Vulnerability Management* shows workloads from `payments` only.
** Other application namespaces (`backend`, `frontend`, `juice-shop`) are not visible.
** Administrative areas such as creating auth providers or broad access-control changes are not available to this user.
. Close the private window and return to your admin session.

TIP: If you see a *nonce verification failed* error, close the private window completely and open a fresh one before retrying. Stale browser state from a previous failed login attempt causes a nonce mismatch.

== Task 3.8: View vulnerabilities in the OpenShift Console

The ACS Console Plugin adds a *Vulnerabilities* tab to Deployment pages in the OpenShift Console.
This gives developers a self-service path to check their own workload findings without switching to ACS Central.

. Open the OpenShift Console URL from your Showroom dashboard.
. Navigate to *Workloads* > *Deployments* and select the `payments` namespace.
. Open a deployment (for example `visa-processor`).
. Click the *Vulnerabilities* tab. Confirm CVE data appears inline with severity and fixable status.

NOTE: If the *Vulnerabilities* tab is not visible, the ACS Console Plugin may not be enabled on this Showroom build. Run `oc get consoleplugin` on the bastion to check. If no `acscs-console-plugin` (or similar) resource exists, skip this task and continue to Cleanup.

This is the same vulnerability data from Exercise 1, surfaced inside the console developers already use. Combined with the scoped role from Task 3.4, a `payments` developer sees only their namespace's findings here as well.

== Key takeaways

* SAC isolates tenants inside one ACS Central using Permission Sets, Access Scopes, and Roles.
* OIDC group mapping assigns those roles automatically from identity group claims.
* Set the *Minimum access role* to *None* on auth providers so only users matching a group rule get access. Leaving the default at Admin defeats the purpose of scoping.
* A scoped login is the proof that multi-tenant ACS works without a separate Central per team.
* The ACS Console Plugin surfaces the same vulnerability data inside the OpenShift Console, giving developers a self-service view without leaving the interface they already use.
