Estimated time: 15 minutes.

Regulatory audits traditionally require teams to spend days aggregating spreadsheet data, zipping CSV files, and distributing them by email.
RHACS replaces that manual workflow with scheduled compliance report generation, configurable delivery destinations, and on-demand evidence downloads tied directly to scan results.

With compliance gaps identified in Exercise 2, the *Information Security* team's next step is producing the evidence package that the auditor will receive: a time-stamped, machine-generated record of every compliance control evaluated against the cluster.

By the end of this exercise you will:

* Open the CIS scan schedule created in Exercise 2 and confirm what remains editable after create.
* Generate an on-demand compliance report in the RHACS UI.
* Fetch the report ZIP from Central on the bastion with the RHACS API and review the CSV as audit evidence.

== Task 3.1: Open the scan schedule detail page

. In the RHACS Console, navigate to *Compliance > OpenShift Schedules*.
. Confirm `cis-audit-schedule` is listed (created in Exercise 2).
+
You may also still see `acs-catch-all` for non-CIS profiles. Use `cis-audit-schedule` for this exercise.
If `cis-audit-schedule` is missing, return to Exercise 2 and create it before continuing.

The schedule *name* is immutable.
+
NOTE: You do not need to change settings for this lab. Editing is optional if you want to update the description for clarity.

== Task 3.2: Generate an on-demand compliance report

On-demand reports let you pull evidence at any time, outside the regular schedule.
This is useful for ad-hoc audit requests or pre-audit preparation.

. From the schedule *detail* page (not only the Schedules list), open the *Actions* drop-down (upper right) and select *Generate download*.
+
You receive a confirmation that report generation has started.
The toast alone is easy to miss. Stay on the detail page and use the jobs tab below.

. Click the *All report jobs* tab on the detail page.
. Watch the job status progress through:
** *Waiting*: The job is queued.
** *Preparing*: The system is collecting and formatting compliance data.
** *Report ready for download*: The report is complete.
. Optional: click *Ready for download* in the UI to save the file in your browser.
The next task runs a script that requests and downloads a report with the bastion API token.
+
NOTE: The Schedules *list* page may also show a *Report ready for download* action after generation completes. Prefer the detail *All report jobs* tab so you can watch status transitions. If you leave the detail page, go back to the Schedules list or reopen `cis-audit-schedule` to find the ready job.

NOTE: Report generation typically completes in under a minute. If the job stays in *Preparing* for more than five minutes, verify that the underlying `ComplianceScan` resources have reached `DONE` (`oc get compliancescan -n openshift-compliance`).

== Task 3.3: Fetch and review the report from the bastion

There is no `roxctl` subcommand for Compliance v2 report ZIP download.
The lab script uses the Central API with the bastion's existing `ROX_API_TOKEN` and `ROX_CENTRAL_ADDRESS`.
It requests its own download job (a browser download is tied to the logged-in UI user and cannot be fetched with the bastion token).

. From the cloned repository, download the report:
+
[source,bash]
----
cd ~/acs-labs
bash scripts/s3-fetch-compliance-report.sh
----
+
The script writes `~/compliance-report.zip` and extracts the CSV under `~/compliance-report/`.
On a single-cluster lab you typically get one CSV (for example `cluster_production_YYYY-MM-DD.csv`).
HTML compliance reports are not part of this lab. The downloadable evidence is a ZIP that contains CSV.
Stop here and confirm the script printed a `CSV=` path before you review the contents.

. Review that CSV:
+
[source,bash]
----
bash scripts/s3-review-compliance-report.sh
----
+
The review prints status counts, a short sample of `FAIL` and `INCONSISTENT` checks, and any tailored-profile rows.
`FAIL` is red, `INCONSISTENT` is yellow, `MANUAL` is cyan, and `PASS` is green.
Confirm columns such as `Control Reference`, `Check(CCR)`, `Profile(version)`, `Profile type`, `Cluster`, `Status`, `Remediation`, and `Rationale`.
The internal check `org-namespace-owner-namespace-owner-label` is in this CSV. Its `Profile type` is `Tailored Profile` and its `Control Reference` is `N/A`, because the check is not a CIS control.

. Cross-check one finding from Exercise 2: confirm the same check name and status appear in the sample.
Compare the `FAIL` count with the Fail findings you saw on Coverage (or the CLI status counts from Exercise 2).

NOTE: Email delivery destinations automate recurring evidence distribution in production (SMTP notifier under *Platform Configuration > Integrations*).
This Showroom does not have SMTP configured, so you used on-demand DOWNLOAD.
In production you would add an auditor distribution list as a delivery destination on the scan schedule and let RHACS email the ZIP on cadence.

== Task 3.4: Operationalizing compliance (reflection)

With scan schedules, delivery destinations, and on-demand reporting in place, consider how this fits into an ongoing compliance program:

* *Continuous visibility*: Daily or weekly scans catch configuration drift before auditors do.
* *Automated evidence delivery*: Email delivery eliminates the manual collection process entirely.
* *Trend tracking*: Comparing reports over time shows whether the compliance posture is improving or degrading.
* *Multi-cluster scale*: The same scan schedule can target multiple clusters, producing consolidated evidence packages.
* *Separation of duties*: Platform Operations remediates infrastructure gaps. Information Security owns schedules and evidence review. Auditors consume the reports. All of that uses RHACS and Compliance Operator results in one system, with role separation rather than separate toolchains.

NOTE: Compliance reporting requires Compliance Operator version 1.6.0 or later. This environment runs version 1.10.0 or newer.

== Key takeaways

* Scan schedules in RHACS manage the full compliance lifecycle: when to scan, what to scan, and who receives the results.
* After create, the schedule *name* is fixed. Description, frequency, profiles, and clusters remain editable.
* The UI *Generate download* path teaches the product workflow. The Central API download path is what automation and bastion CLI workflows use.
* The CSV contains check-level detail suitable for regulatory evidence packages. Cross-referencing it with Coverage or `compliancecheckresults` confirms the downloadable evidence matches the interactive view.
* Operationalizing compliance means continuous scanning, automated delivery, and trend tracking, not periodic fire drills.
