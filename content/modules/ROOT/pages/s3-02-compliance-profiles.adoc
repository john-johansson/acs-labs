= Exercise 1: Deploying compliance profiles
:navtitle: Exercise 1: Deploying compliance profiles

include::partial$session3-ui.adoc[]

Estimated time: 10 minutes.

Most organizations treat compliance as a periodic event: a scramble before an audit to collect evidence, run manual checks, and compile spreadsheets.
The Red Hat Compliance Operator shifts that model to continuous, automated scanning.
It runs natively on OpenShift to evaluate core OS node configurations and platform control plane settings against industry benchmarks, without external agents.

A regulatory audit is scheduled for next quarter.
As the *Platform Operations* team, your first task is to enable continuous CIS benchmark scanning on the cluster so that compliance evidence is generated automatically from this point forward.

You will do that the platform way: apply a YAML `ScanSettingBinding` from the repository with `oc apply`.
That same file-based workflow is what GitOps and CI pipelines use (commit the manifest, let automation apply it).
Exercise 2 shows the RHACS UI alternative for the same profiles.

By the end of this exercise you will:

* List the compliance profiles available on the cluster.
* Deploy a declarative `ScanSettingBinding` that binds the `ocp4-cis` and `ocp4-cis-node` profiles to the default scan settings.
* Apply a `CustomRule` and `TailoredProfile` for an internal ownership control, and leave that profile unbound.
* Watch the CIS scans start. A running scan is enough to continue, because Exercise 2 scans these profiles again.

== Task 1.4: Monitor scan progress

The Compliance Operator creates a `ComplianceSuite` and individual `ComplianceScan` resources.
Scans commonly take several minutes on a multi-node cluster. Use the commands below to see progress. Task 1.3 is the work you do while this scan runs. You do not have to wait for `DONE` before Exercise 2.

. Check per-scan progress:
+
[source,bash]
----
oc get compliancescan -n openshift-compliance
----
+
Re-run the command to watch progress. `PHASE` `DONE` means that scan has finished. `RUNNING` is enough to continue. Exercise 2 deletes this binding and scans the CIS profiles again.
+
TIP: Optional console view (same data, visual status):
+
--
. Open the OpenShift Console URL from the prerequisites.
. Go to *Operators > Installed Operators* and open the *Compliance Operator* (project `openshift-compliance`).
. From the operator pages, open the compliance resources (*ComplianceScan*, *ComplianceSuite*, and related tabs) and refresh to see the current phase. You do not need to wait for `DONE`.
--

. Check suite-level status:
+
[source,bash]
----
oc get compliancesuite -n openshift-compliance
----
+
Example (names and RESULT values vary by cluster):
+
[source,text]
----
NAME              PHASE     RESULT
cis-weekly-scan   RUNNING
----
+
What to check:
+
* Your lab suite is `cis-weekly-scan`.
* `PHASE` may be `RUNNING` or `DONE`. Either is enough to continue. `DONE` means the suite finished. You do not need that before Exercise 2.
* If `RESULT` is already set, it is a high-level summary only. On this lab cluster it is commonly `INCONSISTENT`, `NON-COMPLIANT`, or `ERROR`. That is expected. Do not try to make it `COMPLIANT`.
* Individual check results appear as the scan writes them. A count of zero while `PHASE` is `RUNNING` is fine.

. Verify that individual check results were created:
+
[source,bash]
----
oc get compliancecheckresults -n openshift-compliance --no-headers | wc -l
----
+
A non-zero count means the scan has started writing results. Zero is fine while `PHASE` is still `RUNNING`.

. Summarize check statuses (optional, useful before Exercise 2):
+
[source,bash]
----
oc get compliancecheckresults -n openshift-compliance --no-headers | awk '{print $2}' | sort | uniq -c | sort -rn
----

TIP: Open Exercise 2 once `org-namespace-owner` is `READY`. Coverage for CIS stays empty until the Exercise 2 schedule finishes, because that schedule replaces the CLI binding you applied here. The internal ownership check does not run until Exercise 2 schedules `org-namespace-owner`.

== Key takeaways

* A `ScanSettingBinding` is the declarative link between compliance profiles and scan settings. Applying it triggers scans immediately.
* Applying YAML from a repository is the GitOps and pipeline-friendly path. The RHACS UI (Exercise 2) creates the same kind of binding without writing manifests by hand.
* A `CustomRule` is an organization-specific platform check. A `TailoredProfile` enables it. This lab applies both and leaves them unbound so RHACS can schedule the profile in Exercise 2.
* The Compliance Operator produces `ComplianceScan`, `ComplianceSuite`, and `ComplianceCheckResult` CRDs that capture audit evidence as native Kubernetes resources.
* Suite `RESULT` is a coarse summary (`INCONSISTENT`, `NON-COMPLIANT`, or `ERROR` are all normal here). Treat check-result counts and statuses as the detailed evidence.
