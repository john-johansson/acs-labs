= Exercise 7: Network policy generation
:navtitle: Exercise 7: Network policy generation

include::partial$session3-ui.adoc[]

Estimated time: 15 minutes.

RHACS generates 100% standard Kubernetes `NetworkPolicy` manifests from observed baselines.
There are no proprietary sidecars, no custom CRDs, and no vendor lock-in.
If RHACS were uninstalled tomorrow, OpenShift's OVN-Kubernetes CNI would continue enforcing these policies at the kernel level.
The generated YAML can be committed to a Git repository and applied through a GitOps pipeline.

In this exercise you use the RHACS Network Policy Generator to simulate, review, and apply a zero-trust `NetworkPolicy` for the `postgres` deployment in the `backend` namespace.

The anomalous cross-namespace flow is confirmed.
As *Platform Operations*, you generate and apply zero-trust network policies to block unauthorized paths while preserving the legitimate application flows.

By the end of this exercise you will:

* Open the Network Policy Generator from the Network Graph.
* Generate and simulate network policies for the `backend` namespace.
* Review the auto-generated YAML for `postgres`.
* Apply the policy via CLI and confirm it exists on the cluster.

== Task 7.1: Open the Network Policy Generator

. In the RHACS Console, navigate to *Network Graph*.
. Select your cluster and the `backend` namespace.
. In the graph header, click *Network policy generator*.

== Task 7.2: Generate and simulate policies

. In the panel that opens, click *Generate and simulate network policies*.
+
RHACS generates policies for all deployments in the selected scope based on their observed baseline traffic.
. Review the simulation preview:
** Allowed baseline flows are shown in green.
** Flows that would be blocked by the generated policies are shown in red.

NOTE: Deployments that already have a `NetworkPolicy` will not get a new one. RHACS does not overwrite existing policies.

== Task 7.3: Review the generated YAML

. In the generated policies panel, scroll to the policy for `postgres`. The policy name is `stackrox-generated-postgres`.
. Review the YAML. Expect something similar to:
+
[source,yaml]
----
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: stackrox-generated-postgres
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: postgres
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api-server
    ports:
    - protocol: TCP
      port: 5432
----
+
This policy allows ingress only from pods with label `app: api-server` on port `5432/TCP`.
All other ingress is denied by default once a `NetworkPolicy` exists for a pod selector.
. Click the download icon to save the YAML to your local machine (or copy it to the clipboard).

TIP: To compare the generated policies with existing ones, click *Compare* in the panel. A side-by-side view shows the YAML for current and generated policies.

== Task 7.4: Apply the policy via CLI

. Transfer the downloaded YAML to the bastion (or apply it directly).
. Apply the policy:
+
[source,bash]
----
oc apply -f <downloaded-file>.yaml
----
+
Alternatively, apply the example from the lab repository:
+
[source,bash]
----
oc apply -f content/modules/ROOT/examples/stackrox-generated-postgres.yaml
----
. Verify the policy exists:
+
[source,bash]
----
oc get networkpolicy -n backend
----
+
Expected output includes:
+
[source,text]
----
NAME                          POD-SELECTOR     AGE
stackrox-generated-postgres   app=postgres     5s
----

The OVN-Kubernetes CNI now enforces this policy at the kernel level. Only `api-server` pods can reach `postgres` on port 5432.

== Key takeaways

* The Network Policy Generator produces standard `networking.k8s.io/v1` `NetworkPolicy` manifests, not proprietary resources. OpenShift enforces them natively.
* Generated policies are prefixed with `stackrox-generated-` and labeled with `network-policy-generator.stackrox.io/generated=true` for easy identification and cleanup.
* Policies cannot be applied directly from the RHACS UI. Download the YAML and apply via `oc apply` or commit to Git for GitOps deployment.
* Once a `NetworkPolicy` selects a pod, all ingress not explicitly allowed is denied. This is the Kubernetes default-deny model.
