= Exercise 7: Network policy generation
:navtitle: Exercise 7: Network policy generation

include::partial$session3-ui.adoc[]

Estimated time: 15 minutes.

RHACS generates 100% standard Kubernetes `NetworkPolicy` manifests. Two downloads use different peer lists, and this exercise compares them.
There are no proprietary sidecars, no custom CRDs, and no vendor lock-in.
If RHACS were uninstalled tomorrow, OpenShift's OVN-Kubernetes CNI would continue enforcing these policies at the kernel level.
The generated YAML can be committed to a Git repository and applied through a GitOps pipeline.

In this exercise you use the RHACS Network Policy Generator to simulate, review, and apply a default-deny ingress `NetworkPolicy` for the `postgres` deployment in the `backend` namespace.

The anomalous cross-namespace flow is confirmed.
As *Platform Operations*, you generate and apply that policy so unauthorized paths are blocked while the legitimate application flow remains.

By the end of this exercise you will:

* Mark any Exercise 5 `jump-host` to `postgres` probe as anomalous on the `postgres` baseline.
* Generate a policy from observed flows and see that this probe can still be allowed.
* Apply a `postgres` policy that allows ingress only from `api-server`.

== Task 7.1: Mark the postgres probe as anomalous

Exercise 5 probed `postgres` from `jump-host` to prove baseline alerting.
Marking that probe anomalous updates the baseline and the alerts. It does not change *Generate and simulate network policies*. That button allows every connection observed in the graph time window, including anomalous ones.
The Baseline tab has a separate download, *Download baseline as network policy*. That file omits peers you marked anomalous.

. In the RHACS Console, navigate to *Network > Network Graph*.
. Select the `production` cluster and the `backend` namespace.
. Click `postgres`, then open the *Baseline* tab.
. If `operations/jump-host` (or `jump-host`) appears in the baseline list, use the overflow / bulk actions to *Mark as anomalous*.
. If the flow already shows as anomalous (or is absent from the baseline list), leave it.

== Task 7.2: Open the Network Policy Generator

. Still in *Network > Network Graph* with `backend` selected.
. In the graph header, click *Network policy generator*.

== Task 7.3: Generate and simulate policies

. In the panel that opens, click *Generate and simulate network policies*.
+
RHACS builds one allow list from the connections it observed in the current time window. A flow marked anomalous is still a connection that happened, so `jump-host` can appear in the `postgres` policy because of the Exercise 5 probe. That is expected. Do not mark it anomalous again and generate a second time.
. In the `postgres` YAML, notice whether `jump-host` or the `operations` namespace is allowed.
Peers named in this YAML are the ones the simulated policy would allow.

NOTE: Deployments that already have a `NetworkPolicy` will not get a new one. RHACS does not overwrite existing policies.

== Task 7.4: Review the generated YAML

. In the generated policies panel, scroll to the policy for `postgres`. The policy name is typically `stackrox-generated-postgres`.
. Review the YAML. The intended default-deny ingress policy for this lab looks like:
+
[source,yaml]
----
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: stackrox-generated-postgres
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: postgres
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api-server
    ports:
    - protocol: TCP
      port: 5432
----
+
This policy allows ingress only from pods with label `app: api-server` on port `5432/TCP`.
All other ingress is denied by default once a `NetworkPolicy` exists for a pod selector.

. The policy you apply must allow only `app: api-server` on port `5432`, as in the example above.
+
If the generated `postgres` YAML already matches that example, download it and apply that file in the next task.
+
If it also allows `jump-host` or `operations`, do not apply it. That file is the observed-flow policy. The next task applies the example file instead, which is the api-server-only policy.

TIP: To compare the generated policies with existing ones, click *Compare* in the panel. A side-by-side view shows the YAML for current and generated policies.

== Task 7.5: Apply the policy via CLI

Apply the file that allows only `api-server`.
If the generator download matches the example in Task 7.4, apply that file. Copy it to the bastion first if the browser saved it on your workstation.

[source,bash]
----
oc apply -f ~/stackrox-generated-postgres.yaml
----

If that download allows `jump-host` or `operations`, apply the example file instead:

[source,bash]
----
oc apply -f content/modules/ROOT/examples/stackrox-generated-postgres.yaml
----

Run the example command from the repository root (`~/acs-labs`). Use the saved path if your generator download is not `~/stackrox-generated-postgres.yaml`.

. Verify the policy exists:
+
[source,bash]
----
oc get networkpolicy -n backend
----
+
Expected output includes:
+
[source,text]
----
NAME                          POD-SELECTOR     AGE
stackrox-generated-postgres   app=postgres     5s
----

. Confirm the applied YAML allows only `app: api-server`:
+
[source,bash]
----
oc get networkpolicy stackrox-generated-postgres -n backend -o yaml
----

The OVN-Kubernetes CNI now enforces this policy at the kernel level. Only `api-server` pods can reach `postgres` on port 5432.

== Key takeaways

* The Network Policy Generator produces standard `networking.k8s.io/v1` `NetworkPolicy` manifests, not proprietary resources. OpenShift enforces them natively.
* *Generate and simulate network policies* allows every observed connection in the graph time window, including anomalous flows. *Download baseline as network policy* allows only peers that remain on the baseline.
* Generated policies are prefixed with `stackrox-generated-` and labeled with `network-policy-generator.stackrox.io/generated=true` for easy identification and cleanup.
* Policies cannot be applied directly from the RHACS UI. Download the YAML and apply via `oc apply` or commit to Git for GitOps deployment.
* Once a `NetworkPolicy` selects a pod, all ingress not explicitly allowed is denied. This is the Kubernetes default-deny model.
