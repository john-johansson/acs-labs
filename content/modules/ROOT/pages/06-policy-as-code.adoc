= Exercise 6: Policy-as-code via GitOps
:navtitle: Exercise 6: Policy as code

Estimated time: 15 minutes.

Exercises 3 and 4 used the GUI to toggle enforcement. A `SecurityPolicy` custom resource (CR) lets you define the same policies as YAML — each enforcement action is explicit, and the file lives in Git alongside your application manifests.

`SecurityPolicy` lives in `config.stackrox.io/v1alpha1` (not `platform.stackrox.io`).
The config controller reconciles CRs in the `stackrox` namespace.

== Task 6.1: List the enforcement actions the CR accepts

The CRD schema is the list of legal values. It is not what a particular policy has saved.

. List the allowed enforcement actions:
+
[source,bash]
----
oc explain securitypolicy.spec.enforcementActions --api-version=config.stackrox.io/v1alpha1
----

`FAIL_DEPLOYMENT_CREATE_ENFORCEMENT` and `FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT` are the admission webhook actions that rejected the create in Exercise 4.
`SCALE_TO_ZERO_ENFORCEMENT` is the Deploy switch from Exercise 3.
`FAIL_BUILD_ENFORCEMENT` makes `roxctl image check` return non-zero, which fails a CI/CD pipeline (Exercise 7).
`FAIL_KUBE_REQUEST_ENFORCEMENT` applies to `exec` and port-forward (`k8sevents.stackrox.io`), not to a Deployment create.

== Task 6.2: Review the private-registry policy

You will apply this CR in the next task. Read through it first to understand the key fields.

. Review the CR:
+
[source,yaml]
----
include::example$private-registry-policy.yaml[]
----

Pay attention to these fields:

* `metadata.namespace: stackrox` — the config controller only watches the `stackrox` namespace.
* `negate: true` on the *policy group*, not on the value. This inverts the match: alert when the image registry is *not* `registry.internal.example.com`. Setting `negate` on the value instead of the group is silently ignored — a common mistake when writing CRs by hand.
* `FAIL_DEPLOYMENT_CREATE_ENFORCEMENT` — tells the admission webhook to reject a new `oc apply`. This action is not exposed by the GUI Deploy switch (which stores `SCALE_TO_ZERO_ENFORCEMENT` instead).
* `FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT` — rejects updates to an existing Deployment.
* `SCALE_TO_ZERO_ENFORCEMENT` — Sensor's fallback for workloads that bypassed admission. Also makes `roxctl deployment check` return exit code `1` (Exercise 7).

== Task 6.3: Export the Latest tag clone as a CR

The GUI can export any custom policy as a `SecurityPolicy` CR.

. In *Policy Management*, find *Lab - Latest tag in policy-lab* in the list and click the three-dot menu (⋮) → *Save as Custom Resource*.
+
NOTE: The file downloads to your *local machine* (browser download), not to the bastion where you run `oc`.
. Open the downloaded YAML on your laptop and check `spec.enforcementActions`. The GUI stored `SCALE_TO_ZERO_ENFORCEMENT` — the same action you saw in Task 6.1.
. Copy the YAML content and create a file on the bastion:
+
[source,bash]
----
vi latest-tag-policy.yaml
----
+
Paste the content and save the file. You now have the exported CR on the bastion, ready for `oc apply` or to commit to a Git repository.

In a real environment you would commit this YAML to Git and let Argo CD or a CI/CD pipeline apply it to the `stackrox` namespace. We don't have a Git server or Argo CD instance in this lab, so in the next task we will apply a policy resource directly with `oc apply`.

TIP: If the download does not work, a copy of the policy is available in the cloned repository under `content/modules/ROOT/examples/`.

== Task 6.4: Apply the private-registry policy

. Apply the CR and verify it exists:
+
[source,bash]
----
oc apply -f content/modules/ROOT/examples/private-registry-policy.yaml
oc get securitypolicy lab-enforce-private-registry -n stackrox
----
. In *Platform Configuration → Policy Management*, open *Lab - Enforce Private Registry Only*.
. Compare the GUI view with the CR you just applied.
. The GUI shows *Inform and enforce* with *Deploy* on. It does not show the individual `FAIL_DEPLOYMENT_*` actions — those are only visible in the CR or the API.
. Notice the policy is tagged *Externally managed*. Any edits you make in the GUI will be overwritten the next time the CR is reconciled — this is by design so that Git stays the single source of truth.

== Task 6.5: Dry-run a policy via the API

The private-registry policy is now applied. Before creating more policies, try the dry-run API — it validates a policy definition without saving it, so you can catch errors before committing to Git.

You will use the *Lab - Latest tag in policy-lab* clone (from Exercise 3) as the test subject.

NOTE: The GUI can also export a policy as JSON (three-dot menu → *Save as JSON*), just like the CR download in Task 6.3. Here we use `curl` so the file is created directly on the bastion.

Export it as JSON via the API:

. Export the policy as JSON:
+
[source,bash]
----
POLICY_ID=$(curl -sk -H "Authorization: Bearer $ROX_API_TOKEN" \
  "${ROX_CENTRAL_ADDRESS}/v1/policies" | \
  jq -r '.policies[] | select(.name | test("Lab - Latest tag")) | .id')

curl -sk -H "Authorization: Bearer $ROX_API_TOKEN" \
  "${ROX_CENTRAL_ADDRESS}/v1/policies/${POLICY_ID}" | \
  jq '.' > dryrun-policy.json
----
. Pass it to the dry-run endpoint:
+
[source,bash]
----
curl -sk -X POST \
  -H "Authorization: Bearer $ROX_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d @dryrun-policy.json \
  "${ROX_CENTRAL_ADDRESS}/v1/policies/dryrun" | jq .
----
+
An empty `{"alerts":[]}` means the definition is valid. A non-empty list shows which existing deployments would violate it.

== Key takeaways

* `SecurityPolicy` CRs live in `config.stackrox.io/v1alpha1`, namespace `stackrox`. The config controller reconciles them into Central.
* A CRD can set `FAIL_DEPLOYMENT_CREATE_ENFORCEMENT` directly. The GUI Deploy switch does not expose that action — it stores `SCALE_TO_ZERO_ENFORCEMENT`.
* `oc explain securitypolicy.spec --api-version=config.stackrox.io/v1alpha1` documents every field and enum the CR accepts.
* Private registry enforcement and fixable CVE thresholds are common production patterns — both expressible as `SecurityPolicy` CRs managed via GitOps.
