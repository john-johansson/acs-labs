= Exercise 6: Splunk integration
:navtitle: Exercise 6: Splunk integration

include::partial$session2-ui.adoc[]

Estimated time: 15 minutes.

*Splunk* is a SIEM and log analytics platform: it indexes machine data so security and operations teams can search, correlate, and build dashboards across many sources.
In this exercise you send RHACS policy alerts into Splunk so breaches sit next to the rest of your security telemetry.

*Splunk HEC (HTTP Event Collector)* is a Splunk endpoint that accepts events over HTTPS as JSON.
Applications and security tools POST alerts to an HEC URL with a token, and Splunk indexes those events for search and dashboards.
RHACS uses HEC when you configure the native Splunk notifier, so policy violations can land in Splunk as soon as they fire.

RHACS integrates with Splunk in two ways on this Showroom:

* *RHACS Technology Add-on (TA-stackrox)*: Splunk pulls violations and related data from the RHACS API on a schedule. Events arrive under sourcetype `stackrox-violations`.
* *Native Splunk notifier*: RHACS pushes alerts to Splunk HEC when a policy fires. Events arrive under sourcetype `stackrox-alert`.

By the end of this exercise you will:

* Understand the difference between the pull-based add-on (`stackrox-violations`) and the push-based HEC notifier (`stackrox-alert`).
* Configure an ACS native Splunk notifier with an HEC token and endpoint.
* Trigger a policy violation and verify the alert appears in Splunk search.
* See both sourcetypes side by side and know when to use pull vs push for SOC-style alerting.

== Task 6.1: Open the Splunk console

. On the bastion:
+
[source,bash]
----
oc get route splunk-web -n splunk -o jsonpath='https://{.spec.host}{"\n"}'
----
. Log in with user `admin` and password `RhacsSplunkDemo123!`.
. Go to *Apps* > *Manage Apps*. Type `stackrox` in the search/filter bar and confirm *Red Hat Advanced Cluster Security* (`TA-stackrox`) appears in the results.

== Task 6.2: Check pull-based add-on data

. Return to the Splunk home screen (click the *Splunk>* logo in the top left), then open *Search & Reporting* from the app list.
. Run:
+
[source,text]
----
index=* sourcetype="stackrox-violations"
----
. Expand one event (click the triangle next to it) and look for fields such as `policy` (the ACS policy name that fired), `deployment` (the workload that triggered it), `namespace`, and `severity`.
These are the fields the TA-stackrox add-on pulls from the RHACS API on a schedule.
You will compare these pull-based events with the push-based HEC events you create later in this exercise.
+
TIP: If no fields appear in the event body, click *All Fields* in the left sidebar and tick the relevant ones. Splunk hides fields that are not in the "selected" list by default.

NOTE: The add-on polls on a schedule and may take up to an hour after Showroom provisioning before the first events appear. If the search returns empty, that is expected on a fresh build. Proceed to Task 6.3; the HEC push path does not depend on pull data.

TIP: If `stackrox-violations` returns nothing, try `index=* sourcetype=stackrox*` to discover the actual sourcetype name on your Showroom. Different TA-stackrox versions may use slightly different names.

== Task 6.3: Configure the native Splunk HEC notifier

. Retrieve the HEC token:
+
[source,bash]
----
oc exec deploy/splunk -n splunk -c splunk -- \
  curl -sk -u admin:RhacsSplunkDemo123! \
  "https://localhost:8089/services/data/inputs/http?output_mode=json" 2>/dev/null \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('\n'.join(e['content']['token'] for e in d.get('entry',[]) if e.get('name')!='http'))"
----
. In RHACS, open *Platform Configuration* > *Integrations* > *Splunk*.
. Create integration `Lab - Splunk HEC` with:
+
[cols="1,2",options="header"]
|===
|Field |Value

|HTTP Event Collector URL
|`https://splunk.splunk.svc.cluster.local:8088`

|HTTP Event Collector token
|_(from the command above)_

|Source type
|`stackrox-alert`

|Skip TLS verify
|Enabled
|===
+
. Click *Test*, then *Save*.

TIP: The URL uses HTTPS because the Splunk HEC listener has SSL enabled. The internal service name works because Central and Splunk share the cluster.

== Task 6.4: Clone policies, attach the notifier, and trigger violations

As in Exercise 5, clone the system policies rather than editing them directly.
Attach the Splunk notifier to the clones, then trigger each one.

=== Clone *Curl in Image*

. Navigate to *Platform Configuration* > *Policy Management*.
. In the policy search or filter, find *Curl in Image* and open it.
. Click *Actions* > *Clone policy*.
. On *Details*, set the name to `Lab - Curl in Image Splunk`.
. Open *Policy behavior*.
. In the *Notifiers* section, select `Lab - Splunk HEC`.
. Confirm the clone is *Enabled*, then *Save*.

=== Clone *Alpine Linux Package Manager (apk) in Image*

. Return to *Policy Management*.
. Find *Alpine Linux Package Manager (apk) in Image* and open it.
. Click *Actions* > *Clone policy*.
. On *Details*, set the name to `Lab - APK in Image Splunk`.
. Open *Policy behavior*.
. In the *Notifiers* section, select the same Splunk notifier.
. Confirm the clone is *Enabled*, then *Save*.

Leave the original system policies untouched.

=== Trigger violations

. On the bastion, create two short-lived workloads in `frontend`:
+
[source,bash]
----
oc run splunk-trigger-curl -n frontend --image=registry.access.redhat.com/ubi9/ubi:9.4 --command -- sleep 3600
oc run splunk-trigger-apk --image=docker.io/library/alpine:3.18 -n frontend --command -- sleep 3600
----
+
The UBI 9 image contains `curl`, which triggers the *Curl in Image* policy. The Alpine image contains `apk`, which triggers the *Alpine Linux Package Manager (apk) in Image* policy.
. Wait about 30 to 60 seconds. There is no progress indicator; ACS scans the new images and evaluates policies in the background.
. In the *RHACS Console*, open *Violations* from the left navigation. Filter or search for `splunk-trigger`. Confirm you see alerts for:
** *Lab - Curl in Image Splunk* on `splunk-trigger-curl`
** *Lab - APK in Image Splunk* on `splunk-trigger-apk`
+
This confirms ACS detected the violations. Next you verify the alerts reached Splunk.

== Task 6.5: Verify the alert in Splunk

. Return to the Splunk console. Open *Search & Reporting* (click the *Splunk>* logo, then select it from the app list).
. Run:
+
[source,text]
----
index=* sourcetype="stackrox-alert" | spath | table _time policy.name deployment.name deployment.namespace
----
+
This extracts the JSON fields into columns so you can see the policy name, deployment, and namespace at a glance.
. Confirm you see events tied to *Lab - Curl in Image Splunk* and/or *Lab - APK in Image Splunk* with deployment names `splunk-trigger-curl` and `splunk-trigger-apk` in namespace `frontend`.
+
TIP: If the table is empty, click the triangle next to an event in a plain `index=* sourcetype="stackrox-alert"` search to expand it and inspect the raw JSON. Splunk hides fields that are not in the "selected" set by default.
. Compare pull vs push. Run the add-on search from Task 6.2 alongside the HEC search:
+
[cols="1,1,1,1",options="header"]
|===
|Source |Search |Mechanism |Who set it up?

|TA-stackrox add-on
|`index=* sourcetype="stackrox-violations"`
|Pull (scheduled, broader data set)
|Pre-installed on this Showroom. You did not create this.

|Native Splunk notifier
|`index=* sourcetype="stackrox-alert"`
|Push (real-time, fires per policy violation)
|You created this in Tasks 6.3 and 6.4.
|===
+
The add-on events (`stackrox-violations`) cover historical violations pulled on a schedule by the pre-installed TA-stackrox app. The HEC events (`stackrox-alert`) are the ones you just triggered through the notifier you built. Both sourcetypes can coexist and serve different SOC workflows.

== Key takeaways

* Pull-based add-on (`stackrox-violations`) and push-based HEC notifier (`stackrox-alert`) can run together with different sourcetypes. Use pull for historical coverage and push for real-time SOC alerting.
* The HEC URL must use HTTPS when Splunk has SSL enabled on the collector (the default on this Showroom).
* Clone system policies before attaching notifiers (same pattern as Exercise 5). The clone fires alerts while the system policy stays untouched.
* A notifier only fires for policies that are enabled and have that notifier attached under *Policy behavior*.
