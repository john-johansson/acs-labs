= Exercise 6: Splunk integration
:navtitle: Exercise 6: Splunk integration

include::partial$session2-ui.adoc[]

Estimated time: 15 minutes.

RHACS integrates with Splunk in two ways on this Showroom:

* *RHACS Technology Add-on (TA-stackrox)*: Splunk pulls violations and related data from the RHACS API on a schedule.
* *Native Splunk notifier*: RHACS pushes alerts to Splunk HEC when a policy fires.

You will inspect the add-on, configure (or reuse) the HEC notifier, trigger a violation, and search for the event.

== Task 6.1: Open the Splunk console

. On the bastion:
+
[source,bash]
----
oc get route splunk-web -n splunk -o jsonpath='https://{.spec.host}{"\n"}'
----
. Log in with user `admin` and password `RhacsSplunkDemo123!`.
. Go to *Apps* > *Manage Apps* and confirm *Red Hat Advanced Cluster Security* (`TA-stackrox`) is installed.

== Task 6.2: Check pull-based add-on data

. Open *Search & Reporting*.
. Run:
+
[source,text]
----
index=* sourcetype="stackrox-violations"
----
. If events exist, review fields such as policy, deployment, namespace, and severity.

NOTE: The add-on polls on a schedule. An empty result does not block the HEC push path below.

== Task 6.3: Configure the native Splunk HEC notifier

This cluster may already have a notifier named `Splunk SIEM (local)`.
If it exists and tests successfully, you may reuse it and skip create.

. Retrieve the HEC token:
+
[source,bash]
----
oc exec deploy/splunk -n splunk -c splunk -- \
  curl -sk -u admin:RhacsSplunkDemo123! \
  "https://localhost:8089/services/data/inputs/http?output_mode=json" 2>/dev/null \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('\n'.join(e['content']['token'] for e in d.get('entry',[]) if e.get('name')!='http'))"
----
. In RHACS, open *Platform Configuration* > *Integrations* > *Splunk*.
. Create integration `Lab - Splunk HEC` (or edit the existing local SIEM notifier) with:
+
[cols="1,2",options="header"]
|===
|Field |Value

|HTTP Event Collector URL
|`http://splunk.splunk.svc.cluster.local:8088`

|HTTP Event Collector token
|_(from the command above)_

|Source type
|`stackrox-alert`

|Skip TLS verify
|Enabled
|===
+
. Click *Test*, then *Save*.

TIP: The internal service URL works because Central and Splunk share the cluster.

== Task 6.4: Attach the notifier and trigger a violation

Attach the Splunk notifier to both image policies below, then trigger each one.
Use `Lab - Splunk HEC` (or `Splunk SIEM (local)` if you reused that notifier in Task 6.3).

=== Configure *Curl in Image*

. Navigate to *Platform Configuration* > *Policy Management*.
. In the policy search or filter, find *Curl in Image* and open it.
. Click *Actions* > *Edit policy*.
. On the first step (policy details / lifecycle), set the policy to *Enabled* if it is currently disabled.
. Open *Policy behavior*.
. Under *Notification*, select the Splunk notifier from Task 6.3.
. Review the remaining wizard steps if prompted, then *Save* the policy.

=== Configure *Alpine Linux Package Manager (apk) in Image*

. Return to *Policy Management*.
. Find *Alpine Linux Package Manager (apk) in Image* and open it.
. Click *Actions* > *Edit policy*.
. Set the policy to *Enabled* if it is currently disabled.
. Open *Policy behavior*.
. Under *Notification*, select the same Splunk notifier.
. *Save* the policy.

=== Trigger violations

. On the bastion, create two short-lived workloads in `frontend`:
+
[source,bash]
----
oc run splunk-trigger-curl --image=docker.io/curlimages/curl:8.5.0 -n frontend --command -- sleep 3600
oc run splunk-trigger-apk --image=docker.io/library/alpine:3.18 -n frontend --command -- sleep 3600
----
. Wait about 30 to 60 seconds for image scan and policy evaluation.
. Optional check in RHACS: open *Violations* and confirm alerts for:
** *Curl in Image* on `splunk-trigger-curl`
** *Alpine Linux Package Manager (apk) in Image* on `splunk-trigger-apk`

== Task 6.5: Verify the alert in Splunk

. In Splunk Search, run:
+
[source,text]
----
index=* sourcetype="stackrox-alert"
----
. Open an event and confirm policy and deployment metadata.
. You should see events tied to *Curl in Image* and/or *Alpine Linux Package Manager (apk) in Image*.
. Optional comparison:
+
[cols="1,1,1",options="header"]
|===
|Source |Sourcetype |Mechanism

|TA-stackrox add-on
|`stackrox-violations`
|Pull (scheduled)

|Native Splunk notifier
|`stackrox-alert`
|Push (HEC)
|===

== Cleanup

[source,bash]
----
oc delete pod splunk-trigger-curl splunk-trigger-apk -n frontend --ignore-not-found
----

. For each policy you changed (*Curl in Image* and *Alpine Linux Package Manager (apk) in Image*):
** Remove the Splunk notifier from *Notification*.
** Set the policy back to *Disabled* if you enabled it only for this lab.

== Key takeaways

* Pull (add-on) and push (HEC) can run together with different sourcetypes.
* HEC is the real-time path for SOC-style alerting.
* A notifier only fires for policies that are enabled and have that notifier attached under *Policy behavior*.

[.verification]
****
After creating the trigger pods, does Splunk Search return `index=* sourcetype="stackrox-alert"` events with policy and deployment metadata for *Curl in Image* and/or *Alpine Linux Package Manager (apk) in Image*?
