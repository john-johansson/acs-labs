= Exercise 3: GUI deploy enforcement
:navtitle: Exercise 3: Deploy enforcement

Estimated time: 5 minutes.

So far every policy has been *inform only* — RHACS records a violation, but nothing stops the workload from running.
This exercise flips the switch to *enforce*.
You will deploy a workload that violates a policy, enable enforcement, and observe what happens — and what does *not* happen — to a Deployment that is already running.

When you select *Inform and enforce* and turn *Deploy* on in the GUI, RHACS stores the choice as `SCALE_TO_ZERO_ENFORCEMENT`.
There is no separate "scale to zero" button — the Deploy toggle is that action.
Sensor may set `replicas` to `0` on new workloads that violate the policy, but it does not retroactively scale down a Deployment that was already running when you clicked *Save*.

NOTE: Exercise 4 shows the other enforcement path: a new `oc apply` is rejected outright by the admission webhook.

=== Why clone instead of enforce the system policy?

You can turn enforcement on for any system policy, but a cluster-wide *Latest tag* block would affect every `:latest` image in the Showroom — including infrastructure workloads.
Clone the policy instead: the original keeps informing on every namespace, while the copy enforces only in `policy-lab`.
Criteria on a system policy still cannot be edited, and the policy cannot be deleted.

== Task 3.1: Deploy an image tagged latest

Create a lab namespace and deploy a workload with the `:latest` tag. The `privileged` SCC is for the privileged workload in Exercise 4.

[source,bash]
----
oc new-project policy-lab
oc adm policy add-scc-to-user privileged -z default -n policy-lab
oc create deployment test-latest-tag --image=image-registry.openshift-image-registry.svc:5000/openshift/httpd:latest
oc get deploy test-latest-tag -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
----

Wait until the Deployment is `1/1`.

The system policy *Latest tag* matches this Deployment and records a violation, but the Deployment is created and running.
That is because the policy is still set to *Inform only* — it observes and reports, but does not block or scale anything.

== Task 3.2: Clone Latest tag and enforce it in policy-lab

. From the *Policy Management* list, open *Latest tag*.
. Click *Actions → Clone policy*.
. On *Details*, set the name to `Lab - Latest tag in policy-lab` and the severity to *High*. Click *Next*.
. On *Rules*, leave the image-tag rule as `latest`. Click *Next*.
. On *Resources*, include only the namespace `policy-lab`. Click *Next*.
. On *Behavior → Actions*, select *Inform and enforce* and turn *Deploy* enforcement on. Leave *Build* enforcement off. Click *Next*.
. On *Review policy*, verify the preview shows only matched deployments from `policy-lab` (the namespace name is not displayed in the results — confirm you see `test-latest-tag` and no workloads from other namespaces). Click *Save*.

The system policy keeps informing on every namespace.
The clone enforces only in `policy-lab`.

== Task 3.3: The running Deployment is unchanged

. Return to the RHACS console and open *Violations*.
. Open the violation for deployment `test-latest-tag` and policy *Lab - Latest tag in policy-lab*.
. The *Deploy* switch you turned on is stored as `SCALE_TO_ZERO_ENFORCEMENT`. That is Sensor setting `replicas` to `0`, not a second control in the wizard.

[source,bash]
----
oc get deployment test-latest-tag -n policy-lab
----

`READY` is still `1/1`.
Sensor does not scale a Deployment that was already admitted when you clicked *Save*.
A later manual scale-up is not pulled back down. Sensor applies scale-to-zero once.

NOTE: Exercise 4 uses *Privileged Container* to show what a *new* `oc apply` does after Deploy enforcement is on. The admission webhook rejects that create.

== Cleanup

Before Exercise 7, disable `Lab - Latest tag in policy-lab` and delete this Deployment. Leave the system policy *Latest tag* enabled.

[source,bash]
----
oc delete deployment test-latest-tag -n policy-lab --ignore-not-found
----

== Key takeaways

* You can enforce a system policy, but a cluster-wide *Latest tag* block is the wrong scope. Clone it so the original keeps informing everywhere.
* A narrower scope is a different purpose. Keep the built-in policy so the rest of the cluster is still informed.
* *Inform and enforce* with *Deploy* on is stored as `SCALE_TO_ZERO_ENFORCEMENT`. It records the violation and leaves an already-running Deployment at 1 replica. A new create is rejected by the admission controller, which Exercise 4 demonstrates.
