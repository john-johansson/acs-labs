Estimated time: 15 minutes.

In Exercise 1 you deployed scans from the CLI using a `ScanSettingBinding`.
That approach works well for GitOps pipelines, but RHACS also provides a full UI workflow for creating scan schedules, selecting profiles, and managing compliance operations.
In this exercise you create a scan schedule through the RHACS console, triage the compliance results, and work with the remediation guidance to identify what needs to change before the audit.

Platform Operations has deployed the scans.
Switching to the *Information Security* perspective, your job is now to verify whether the cluster meets CIS requirements and identify the gaps that need remediation before the auditor arrives.

By the end of this exercise you will:

* Create a compliance scan schedule through the RHACS UI.
* Configure scan settings: profile selection, cluster scope, and schedule frequency.
* Navigate the Coverage page and compare profile coverage.
* Find a specific failing check, read its remediation guidance, and understand what needs to change.

== Task 2.1: Create a scan schedule via the RHACS UI

Exercise 1 used `oc apply` to create a `ScanSettingBinding` directly.
RHACS provides the same capability through its console, which is how most Information Security teams manage compliance day-to-day.

. In the RHACS Console, navigate to *Compliance > OpenShift Schedules*.
+
You should see the `acs-catch-all` schedule (or any schedule the Compliance Operator created automatically).

. Click *Create scan schedule*.
. Configure the schedule:
.. *Name*: `cis-audit-schedule`
.. *Description*: `Weekly CIS scan for Q4 audit evidence`
.. *Schedule*: Select *Weekly* and pick a day (e.g., Monday).
.. *Profiles*: Select `ocp4-cis` and `ocp4-cis-node` from the profile list.
.. *Clusters*: Select `production` (or all clusters).
. Click *Create* to save the schedule.
+
RHACS creates the underlying `ScanSettingBinding` on the cluster automatically.
This is the equivalent of the `oc apply` step in Exercise 1, but managed entirely through the UI.

. Verify the new schedule appears in the list alongside any existing schedules.

NOTE: Both the CLI-created `cis-weekly-scan` and the UI-created `cis-audit-schedule` produce `ComplianceCheckResult` CRDs on the cluster. RHACS aggregates results from all schedules on the Coverage page.

== Task 2.2: Explore profile coverage and scan settings

Before reviewing results, explore what each profile covers.

. On the *Compliance > OpenShift Schedules* page, click your `cis-audit-schedule` to open the detail view.
. Review the *Configuration* tab:
** *Profiles*: Which CIS benchmarks are included.
** *Clusters*: Which clusters the scan targets.
** *Schedule*: The recurrence pattern.
+
These settings can be edited at any time by clicking the *Edit* button (pencil icon).

. Navigate to *Compliance > OpenShift Coverage*.
. Use the *Profile* dropdown to switch between `ocp4-cis` and `ocp4-cis-node`:
** `ocp4-cis`: Platform-level controls (API server flags, etcd encryption, RBAC settings). These are cluster-wide checks.
** `ocp4-cis-node`: Node-level controls (kernel parameters, file permissions, kubelet configuration). These run on every node.
. Compare the check counts and compliance percentages between the two profiles.
+
Most clusters show a lower compliance percentage for `ocp4-cis-node` because it covers a larger number of OS-level hardening controls.

== Task 2.3: Find and triage a specific failing check

Rather than browsing the full list, work through a targeted triage workflow.

. On the Coverage page, ensure the *Checks* view is selected.
. Use the *Status* filter to show only *Fail* checks. This narrows the view to controls that need attention before the audit.
. Sort by *Fail* count (descending) to prioritize checks that affect the most resources.
. Find the CIS check for *API server TLS certificates* (look for a check name containing `api-server` and `tls` or `cert`, or browse the 1.2.x control references).
+
If that specific check is not failing, select any check with a *Fail* count greater than zero.
. Click the check name to open the detail view.

== Task 2.4: Work with remediation guidance

This is where RHACS goes beyond a simple pass/fail report.
Each failing check includes remediation guidance that tells an administrator exactly what to change.

. In the detail panel, review:
** *Description*: What the control evaluates and why it matters.
** *Rationale*: The security reasoning behind the control.
** *Failing entities*: Which cluster nodes or platform resources failed.
** *Remediation*: Specific instructions for bringing the resource into compliance.
+
This is the "pointer to the fix" concept: RHACS does not just report failures, it links directly to the resource that needs remediation and explains what to change.

. Note the remediation instruction. In a real audit preparation workflow, you would:
.. File a ticket for Platform Operations with the remediation steps.
.. Re-scan after the fix to confirm the check passes.
.. Generate the evidence report (Exercise 3) showing the improved posture.

. Navigate back and click a second failing check from a different profile (e.g., if you first reviewed a platform control from `ocp4-cis`, now pick a node control from `ocp4-cis-node`).
. Compare the remediation guidance: platform checks typically reference API server or etcd configuration, while node checks reference file permissions or kubelet flags.

NOTE: Some checks show a *Manual* status. These are controls that require human judgment (e.g., reviewing organizational policies). They cannot be evaluated automatically and are flagged for manual review during audits.

== Task 2.5: Understand platform vs workload compliance

The Coverage page shows *infrastructure and platform compliance* evaluated by the Compliance Operator:

* Node-level controls (e.g., kernel parameters, file permissions, kubelet configuration) use the `ocp4-cis-node` profile.
* Platform controls (e.g., API server flags, etcd encryption, RBAC settings) use the `ocp4-cis` profile.

RHACS also evaluates *workload runtime security* through its policy engine (e.g., non-root container execution, privilege escalation prevention, resource limits).
These workload checks are not part of the Compliance Operator profiles and do not appear on the Coverage page.
They are visible under *Violations* and *Policy Management* in the RHACS console.

NOTE: The Coverage page filters by scan schedule, profile, cluster, and compliance status. Namespace-level workload compliance filtering is not available here because the Compliance Operator evaluates cluster-wide infrastructure, not per-namespace workload posture.

== Key takeaways

* RHACS provides both UI and CLI workflows for managing compliance scans. The UI approach (*Compliance > OpenShift Schedules*) is how most teams manage compliance day-to-day.
* Creating a scan schedule in the RHACS UI generates the same `ScanSettingBinding` CRDs as the CLI approach in Exercise 1.
* The Coverage page is more than a dashboard. Drilling into a failing check gives you the description, rationale, affected resources, and specific remediation instructions.
* A targeted triage workflow (filter by Fail, sort by count, drill into specifics) is more efficient than browsing the full check list.
* *Manual* checks require human judgment and cannot be automated. They are flagged for review during audits.
* Infrastructure compliance (Compliance Operator) and workload runtime security (RHACS policy engine) are complementary. Together they cover the full security posture from OS settings to container behaviour.
