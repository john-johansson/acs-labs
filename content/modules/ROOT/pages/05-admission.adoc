= Exercise 4: Inform-only vs admission rejection
:navtitle: Exercise 4: Admission control

Estimated time: 15 minutes.

Exercise 3 turned on Deploy enforcement and left the running Deployment in place.
This exercise proves the other path: a new `oc apply` is rejected by the admission webhook, and the object never lands in etcd.

On this cluster the admission controller is already watching *CREATE* and *UPDATE* (`listenOnCreates: true`, webhook `policyeval.stackrox.io`).

TIP: *Hard vs soft enforcement.* When the admission webhook blocks a create, the object never reaches `etcd` — that is *hard enforcement*. When the webhook is bypassed, disabled, or times out, the object is admitted and Sensor scales the pods to zero instead — that is *soft enforcement*. Soft enforcement is a safety net, not a replacement for the webhook.

[cols="1,3",options="header"]
|===
|When the policy is…
|What `oc apply` does

|*Inform only*
|The Deployment object is created. Violations appear in the console.

|*Inform and enforce (Deploy)*
|The API request is *denied*. The object never lands in etcd.
|===

*Scale-to-zero* (`SCALE_TO_ZERO_ENFORCEMENT`) is the Sensor fallback for workloads that already exist or that bypass admission.
It is also the action `roxctl deployment check` treats as *BREAKS DEPLOY* (exit code 1).
It is *not* the webhook that rejects creates.

`FAIL_KUBE_REQUEST_ENFORCEMENT` is a different action: it applies to Kubernetes *events* such as `exec` / `port-forward` (webhook `k8sevents.stackrox.io`), not to Deployment CREATE.

== Task 4.1: Inform-only — object is created

Deploy a privileged workload while the system policy *Privileged Container* is still set to *Inform only*:

[source,bash]
----
oc apply -n policy-lab -f content/modules/ROOT/examples/privileged-app.yaml
----

[source,bash]
----
oc get deployment test-privileged-app -n policy-lab
----

The Deployment *is created* (`spec.replicas=2`).
ACS records a Deploy violation, but does not block the API request — the policy is inform-only.

== Task 4.2: Clone Privileged Container and enforce it

Just like Exercise 3, do not enforce the system policy directly — that would block privileged workloads across the entire cluster.
Clone it and scope enforcement to `policy-lab`.

. In *Platform Configuration → Policy Management*, open *Privileged Container*.
. Click *Actions → Clone policy*.
. On *Details*, set the name to `Lab - Privileged Container in policy-lab`. Click *Next*.
. On *Rules*, leave the privileged container criterion as-is. Click *Next*.
. On *Resources*, include only the namespace `policy-lab`. Click *Next*.
. On *Behavior → Actions*, select *Inform and enforce* and turn *Deploy* enforcement on. Click *Next*.
. On *Review policy*, verify the preview shows only `test-privileged-app`. Click *Save*.

== Task 4.3: Webhook rejects a new create

Delete the existing Deployment and try to recreate it:

[source,bash]
----
oc delete deployment test-privileged-app -n policy-lab --ignore-not-found
----

[source,bash]
----
oc apply -n policy-lab -f content/modules/ROOT/examples/privileged-app.yaml
----

Expected output:

[source,text]
----
Error from server (Failed currently enforced policies from RHACS): admission webhook "policyeval.stackrox.io" denied the request:
The attempted operation violated one or more enforced policies, described below:

Policy: Lab - Privileged Container in policy-lab
- Violations:
    - Container 'nginx' is privileged

In case of emergency, add the annotation {"admission.stackrox.io/break-glass": "ticket-1234"} to your deployment
----

== Task 4.4: Find the denied create on the Violations page

. Return to the RHACS console and open *Violations*.
. Switch to the *Attempted* tab. This tab lists requests that the admission webhook denied.
. Open the violation for *Lab - Privileged Container in policy-lab*.
. The detail shows the blocked create: container `nginx` is privileged. There is no Deployment behind it because the API server rejected the request.

== Task 4.5: Break the glass

Sometimes enforcement must be bypassed — a critical hotfix, a debugging session, or a workload that legitimately needs privileged access.
RHACS provides a controlled escape hatch: the `admission.stackrox.io/break-glass` annotation.
Adding it to the manifest tells the admission webhook to allow the request through despite the policy violation.

The annotation must be on the manifest *before* the `CREATE` request reaches the API server.
Using `oc annotate` on an existing object sends a `PATCH`, which is not intercepted by the webhook — so it must be in the YAML itself.

. Apply the break-glass manifest:
+
[source,bash]
----
oc apply -n policy-lab -f content/modules/ROOT/examples/privileged-app-break-glass.yaml
----
+
The Deployment is created despite the enforcing policy.
. Open *Violations* and filter on *Emergency Deployment Annotation*.
. Open the violation for `test-privileged-app`.
. The annotation value `lab-exercise-4` is recorded in the deployment details.

RHACS always fires the *Emergency Deployment Annotation* policy when this annotation is present, so every bypass is auditable.

== Cleanup

Delete the clone and the test deployment so later exercises are not blocked.
The system policy *Privileged Container* was never modified — it stays at *Inform only*.

. In *Policy Management*, delete *Lab - Privileged Container in policy-lab*.
. Delete the test deployment:
+
[source,bash]
----
oc delete deployment test-privileged-app -n policy-lab --ignore-not-found
----

== Key takeaways

* *Inform only* creates the object and records a violation. *Inform and enforce* with *Deploy* on rejects the API request before the object is stored.
* The admission webhook `policyeval.stackrox.io` handles `CREATE`, `UPDATE`, and `SCALE`. It does not act on a Deployment that is already running (Exercise 3).
* Denied creates appear on the *Violations* page under the *Attempted* tab.
* In a CRD, this behavior is `FAIL_DEPLOYMENT_CREATE_ENFORCEMENT` and `FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT` (Exercise 6). The GUI Deploy switch stores `SCALE_TO_ZERO_ENFORCEMENT`, which is Sensor's fallback.
* The `admission.stackrox.io/break-glass` annotation bypasses the webhook. The *Emergency Deployment Annotation* policy alerts on its use.
* The `contactImageScanners` setting on the `SecuredCluster` CR controls whether the admission controller can evaluate *image-based* policy criteria (CVEs, packages, registries). The default is `DoNotScanInline` — the webhook cannot check image contents, so it fails open and Sensor does soft enforcement instead. Set it to `ScanIfMissing` if you need the webhook to hard-block on image criteria. Be aware that scanning adds latency; if the `timeoutSeconds` value (default 10) is too low, the webhook may still time out and fail open.
